人気イベントのチケット予約サービス（座席指定あり）を設計する場合、発売開始直後の「スパイクトラフィック」に対応しつつ、「1 つのチケットを複数人购买する」というデータ不整合を防ぐことが最大の鍵となります。面接での評価基準である思考プロセスに沿って、優先順位の高い順に説明します。

### 1. 要件定義と規模感の概算 (Scope & Estimation)
設計に入る前に、以下の数値を仮定して QPS（秒間クエリ数）やデータ量を推計する必要があります。これがスケーリングの根拠になります。

*   **想定ユーザー**: DAU 1000 万人と仮定
*   **アクセス集中度**: 発売開始直後は通常時の数百倍〜数千倍に達するスパイクが発生すると予想されるため、最大同時接続数や QPS は通常時ではなく「ピーク時」で設計する必要があります。
    *   例: 1 秒あたりの予約リクエストが 10 万回程度と想定する場合、データベースへの負荷は非常に高いです。
*   **可用性要件**: イベント当日の購入失敗は致命的なため、「高可用性（High Availability）」を最優先し、RPO/RTO を厳格に設定します。

### 2. 核心となる課題の特定 (Bottleneck Identification)
この問題設計において最も重要で難しいのは以下の 2 つです。

1.  **在庫管理と競合処理**: 複数のリクエストが同時に同じ席を予約した場合、どうして重複購入を防ぐか（データ一貫性）。
2.  **スパンキングな負荷への耐性**: 数万人のユーザーが同時アクセスした際のレスポンス速度（パフォーマンス）。

### 3. ハイレベル設計 (High-Level Design)
全体の構成を以下の要素で分割します。

*   **クライアント層**: Web アプリ / モバイルアプリ。リクエストは API Gateway に集約されます。
*   **プレゼンテーション層 (API Server)**: ロジック処理を担当し、複数インスタンスで水平スケーリングできます。
    *   **レート制限 (Rate Limiting)**: ユーザーや IP ごとに一定のリクエスト数を制限し、サーバーを保護します。
    *   **トランザクション管理**: DB アクセスの制御を行う場所です。
*   **キャッシュ層 (Redis など)**:
    *   **在庫情報（残席数）と座席状態**は頻繁に更新されるため、RDBMS ではなく NoSQL または Redis を使用し、読み書きを高速化します。
    *   **Lua スクリプト**: 在庫の減算と予約の確認を原子操作として実行し、競合を防ぎます。
*   **データストア層 (PostgreSQL など)**:
    *   最終的な決済情報やユーザーデータを保持します。Redis で管理された座席状態が確定したら、RDBMS に永続化（Flush）します。
*   **アシンク処理**:
    *   予約成功後のメール送信など、非同期でキューに積んで処理することで、メインフローのボトルネックを防ぎます。

### 4. ボトルネック対策と詳細設計 (Deep Dive)
ここが技術的な深掘りのポイントとなります。

#### A. データベースのシャーディング戦略
全ての席データを一つのテーブルに入れると、ロック競合が発生しやすくなります。

*   **パーティショニング**: イベント ID または座席番号のハッシュ値を使って、レコードを複数のデータベースインスタンス（または同じ DB の異なるパーティション）に分散させます。これにより、特定のイベントへのアクセスが集中しても、他のテーブルには影響を与えません。
*   **ロック粒度**: 全てのレコードを「書き込み専用」とするとパフォーマンスが落ちるため、「楽観的ロック」や「行レベルの排他制御」を検討します。ただし、高頻度更新のため、Redis レベルでの在庫管理を行い、RDBMS は最終確定時のみアクセスさせるのが一般的です。

#### B. キャッシュと在庫管理 (Critical Path)
最も重要な部分です。重複予約を防ぐために、以下の構成を採用します。

1.  **事前準備**: イベント発売前に Redis に全ての座席状態（「空き」「保留」「購入済み」）を格納し、「残席数」としてハッシュテーブルとして保持します。
2.  **リクエストフロー**:
    *   ユーザーが「席 A-10」を購入しようとする。
    *   API サーバーは Redis の該当キーに対して、Lua スクリプトを実行させます。「残りがあれば、カウントを減らして予約成功」という処理を原子操作（Atomic Operation）として行います。これにより、別のプロセスが同時に同じ席を買おうとしても失敗します。
3.  **永続化**: Lua スクリプトで「購入可能」と判定された後、RDBMS に予約記録を作成し、Redis を更新（または削除）。

#### C. パフォーマンス最適化
*   **CDN の活用**: HTML ページや画像を CDN で配信し、サーバー負荷を減らします。ただし、動的な在庫情報はキャッシュできないため注意が必要です。
*   **接続プーリングとスレッドプール**: API サーバー側で DB への接続数制限を行い、リソース枯渇を防ぎます。

### 5. 拡張性と高可用性 (Scalability & HA)
*   **水平スケーリング**: API サーバーはロードバランサーの後ろに複数配置し、トラフィックに応じて自動スケールします（Kubernetes など）。
*   **データベースのレプリケーション**: マスター - スレーブ構成で読み書き分離を行い、リードスパンキング時の読み取り負荷を軽減します。
*   **フェイルオーバー**: 特定のノードが落ちても、他のインスタンスにリクエストが転送されるように設計します。

### まとめ
この問題では、「高負荷時にデータの一貫性を保つこと」が最も重要です。単なる RDBMS の使い分けではなく、**Redis を活用した原子操作（Lua スクリプト）による在庫管理**と、**データベースへのシャーディング戦略**を組み合わせることで、大量の同時アクセスに対する耐性を持たせます。また、非同期処理で冗長化し、システム全体の安定性を確保する構成が適切です。
