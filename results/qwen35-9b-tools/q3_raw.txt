# リアルタイムチャットシステムの設計

## 1. スケール性と高可用性（最優先）

リアルタイムチャットは常に接続されたユーザーがいます。以下の対策が必要です：

- **水平スケーリング**：メッセージサーバーを複数インスタンスで構成し、負荷分散を行う
- **Sharding戦略**：ルームIDやユーザーIDに基づきデータを分けることで単一ノードへの集中を防ぐ
- **クローン・レプリケーション**：DB とキャッシュ（Redisなど）の冗長化により障害時の可用性を確保

## 2. メッセージ配信アーキテクチャ

### WebSocket の採用とファールオーバー
リアルタイム通信には WebSocket が最適です。しかし、WebSocket サーバーは高負荷時に接続数制限に直面します。
- **WebSockets + HTTP Fallback**：WebSocket で常時接続し、障害時は HTTP/Polling にフォールバックする設計を検討
- **接続管理層の分離**：メッセージ処理ロジックと WebSocket 接続を別のレイヤーで実装

### メッセージ配信パターン
```
┌───────────┐    ┌──────────────┐    ┌───────────┐
│   Sender  │───▶│ Message Q /  │───▶│ Recipient │
│           │     │ Pub/Sub Broker│    │ WebSocket │
└───────────┘    └──────────────┘    └───────────┘
```

## 3. オフラインユーザー復帰時のメッセージ処理（重要）

### 課題の理解
- ユーザーがオフライン中に送信されたメッセージをどう保持するか
- リアプコンectした瞬間に過去の未読メッセージを受信する際、パフォーマンスへの影響
- メッセージ欠落・重複防止の保証

### アプローチ

#### A. メッセージキューと永続化
```
[メッセージ] → [Pub/Sub Queue] → [Persistence DB] ← 追跡ID付き
```

**重要な設計点：**
1. **永続化と非同期配信**：まず信頼性のあるDBに保存し、後から WebSocket で配信する
2. **Cursor-based pagination**：オフラインユーザーが復帰時に「どこから」メッセージを取得すべきかを cursor（最後に受信したメッセージID）で管理

#### B. リアプコンect 時の処理フロー
```
1. ユーザー接続 → 最終メッセージIDの取得 ← Redis/DB から
2. クライアントに「未読メッセージ数」と「cursor」を送信
3. サーバーが cursor より新しいメッセージをフィルタリングして配信
4. メッセージ送信時にクライアントへの確認（ack）を要求

注意点：大量の過去メッセージを一括で送信するとパフォーマンス低下するため、以下対策が必要
```

#### C. パフォーマンス最適化
- **バッチ処理**：一度に 10〜50 のメッセージではなく、500〜1000 に分割して送信
- **クライアント側のフィルタリング**：サーバー側で全メッセージを送らず、クライアントがローカル保存済みと判断すればスキップ
- **スライディングウィンドウ**：過去3分以内のメッセージだけ配信し、古いものは「アーカイブ」として別途提供

## 4. データ永続化戦略

### システム構成案
```
┌─────────────┐     ┌──────────────┐     ┌─────────────┐
│   Client    │◀───▶│ WebSocket    │◀───▶│ Pub/Sub MQ  │
│ (Socket.io) │     │ Node.js +    │     │ RabbitMQ/Kafka│
└─────────────┘     │ Redis Cache  │     └─────────────┘
                    │ PostgreSQL   │
                  └───────┬─────────┘
                          ▼
              ┌──────────────────────┐
              │   Message Storage    │
              │ (PostgreSQL + Shard) │
              └──────────────────────┘
```

### データベース設計のポイント
- **分片（Sharding）**：ルームIDまたはユーザーIDでデータを分けることで、単一テーブルのサイズ制限を回避
- **メッセージ履歴**：過去のメッセージは PostgreSQL で保存し、頻繁にアクセスされるものは Redis にキャッシュ

## 5. セキュリティ対策

- **認証・認可**：JWT を使用したセッション管理とルームメンバー権限チェック
- **暗号化**：通信経路の TLS と送信内容の end-to-end 暗号化（オプション）
- **レート制限**：スパム防止のためのメッセージ送信頻度制限

## まとめ：設計の優先順位

1. **可用性と拡張性** → システムが常に稼働し、ユーザー増加に対応可能であること
2. **オフライン復帰時の整合性** → メッセージ欠落・重複を防ぎ、パフォーマンスへの影響最小化
3. **配信効率** → 大量メッセージ送受信による負荷分散と最適化
4. **データ永続化** → リスク管理（DB シンク）とキャッシュ戦略の両立
5. **セキュリティ** → プライバシー保護と不正アクセス防止

この設計は、Slack や Discord のような大規模チャットアプリの実装において実際に採用されているベストプラクティスを反映しています。
